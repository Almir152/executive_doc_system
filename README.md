# Единая система управления исполнительной документацией

Настольное приложение для учёта исполнительной документации строительного
объекта по техническому заданию (115 разделов).

> **Статус разработки.** Закрыты **Этапы 0–7**: слой данных и миграции схемы,
> нормативные формы, рабочее окно проекта, редактор формы документа, печать
> по ТЗ и выпуск версий, комплекты с реестром, BACKUP/восстановление,
> обновление программы без потери данных и ИИ-агент с черновиками
> и подтверждением оператора. Критерий функциональной готовности (ТЗ п.110)
> закрыт сквозным сценарием `tests/test_stage8_full_scenario.py`.
> Точный перечень — в разделах «Что уже работает» и «Что не реализовано».
> Не обещайте заказчику то, чего в коде нет.

## Что уже работает (Этапы 0–7)

* **Рабочее окно проекта** (ТЗ п.16): открывается двойным щелчком по проекту;
  показывает карточку, проектную документацию, документы, связанные файлы,
  комплекты и историю. Карточка правится отдельной операцией (ТЗ п.17).
* **Проектная документация** (ТЗ п.21): разделы с неограниченным количеством,
  уникальным кодом внутри проекта и защитой от удаления, если в проекте есть
  выпущенные версии документов.
* **История проекта** (ТЗ п.86): каждое изменение карточки и другие операции
  пишутся в ту же транзакцию, что и сами данные.
* **Редактор формы документа** (ТЗ п.65): открывается в рабочей области окна
  проекта, поля строятся по описанию нормативной формы (ТЗ п.96), а не по коду.
* **Черновик незавершённой формы** (ТЗ п.66): сохраняется без проверки
  обязательных полей; при закрытии формы с несохранённым вводом предлагается
  сохранить черновик, отменить закрытие или закрыть без сохранения.
* **Выбор справочных значений с поиском** (ТЗ п.20): организации, представители
  и виды разделов выбираются из справочника с поиском по мере набора, в любом
  регистре кириллицы. Свободный ввод для справочных значений недоступен.
* **Проверка комплекта перед выгрузкой** (ТЗ п.82, 83): комплект
  проверяется до выгрузки; при замечаниях оператор видит их перечень и решает,
  выгружать ли всё равно. В этом случае в папке текущей выгрузки появляется
  `Ошибки выгрузки.txt`; ранее созданные комплекты не меняются.
* **Открытие формы** (ТЗ п.65): режим открытия выбирается один раз для
  приложения — внутри правой рабочей области или отдельно; форму можно
  развернуть на весь экран проекта и вернуть прежний размер.
* **Создание и правка раздела** (ТЗ п.21, 22): один диалог с реквизитами
  раздела, выбор вида раздела, организации и проектировщика — с поиском;
  код раздела при правке не меняется, так как он участвует в именах папок
  комплекта (ТЗ п.70).
* **Выбор разделов проекта в форме** (ТЗ п.21): поле со ссылкой на разделы
  заполняется отметкой нужных разделов, а не текстом; выбор сохраняется
  вместе с черновиком.
* **Блоки подписантов** (ТЗ п.63): «Сдал» и «Принял» — два независимых блока,
  каждый заполняется или не заполняется сам по себе.
* **Незаполненный представитель эксплуатации** (ТЗ п.64): решение «оставить
  пустую строку» или «убрать блок из печати» предлагается перед сохранением,
  относится к конкретному документу и сохраняется в одной транзакции с
  черновиком. Убрать блок можно только там, где это допускает форма
  (АОУСИТО и акты испытаний, ТЗ п.40); в остальных формах вопрос не задаётся.

* **Проекты:** создание, просмотр, удаление с подтверждением. Направление работ
  из ТЗ п.14 (общестроительные / внутренние сети / наружные сети).
* **Единый архив файлов** с дедупликацией по SHA-256: один физический файл —
  одна копия на диске (ТЗ п.84, 92). Повторная загрузка того же файла новой
  копии не создаёт.
* **Архив разделён на два уровня** по ТЗ п.90, 91: логический `ArchiveDocument`
  и физические версии `ArchiveFileVersion`. Одна копия файла на версию.
* **Версии файлов:** новая редакция схемы создаёт новую версию, а прежняя
  сохраняется (ТЗ п.53, 93). Актуальной помечена ровно одна версия.
* **Связи с ролями и закреплением версии** (ТЗ п.47, 49, 91): одна схема
  связывается с любым числом актов, и уже сформированные комплекты продолжают
  ссылаться на ту редакцию файла, которая использовалась при их создании.
* **Доменные модели по ТЗ п.89:** организации и представители, разделы проекта,
  материалы, документы с подтипами АОСР/АООК/АОУСИТО/акт испытаний, блоки
  подписантов «Сдал»/«Принял», комплекты с нумерацией реестра, история.
* **Нормативные формы описаны как данные** (ТЗ п.24, 96) и загружены в
  справочник `normative_forms`: АОСР, АООК, АОУСИТО и акт испытаний. Форма
  задаёт разделы, источник каждого значения (вручную / из проекта / из архива),
  неизменяемые формулировки и правила вроде порога «5 документов -> реестр».
  Перед сохранением описание проверяется на соответствие ТЗ: форма, нарушающая
  п.25-28, 30-32 или 35-41, в базу не попадает.
* **Версионирование форм** (ТЗ п.96): изменение формы под занятым номером
  версии отклоняется — требуется новая версия; прежняя остаётся в базе, и
  документы, выпущенные по ней, сохраняют её.
* **Версионирование схемы БД** (ТЗ п.97): миграции применяются один раз,
  фиксируются в `PRAGMA user_version`, каждая — в своей транзакции.
* **Защита от потери файлов:** архивные документы не удаляются каскадом вместе
  с проектом — ограничение держит сама БД (ТЗ п.54, 109).
* **Категории архива** по ТЗ п.50: материалы и документы качества,
  исполнительные схемы, протоколы и обследования, архив проекта.
* **Защита от удаления используемого файла** (ТЗ п.50, 109).
* **Проверка хронологии АООК ↔ АОСР** (ТЗ п.33, 87) — как библиотечная функция;
  подключение к формам запланировано в Этапе 4.
* **AI Connector:** три режима по ТЗ п.9 (нет ИИ / локальный / интернет-ИИ) с
  индикацией; при «Нет ИИ» чат скрывается. ИИ не имеет доступа к БД и файлам.
* **Целостность БД:** внешние ключи проверяются при каждом подключении, и если
  прагма не сработала (файл базы занят другим процессом), программа отказывается
  работать с понятным сообщением, а не продолжает без контроля связей.
* **Обычный режим журнала SQLite:** база принудительно выводится из WAL, иначе
  последние коммиты лежали бы в `app.db-wal` и копия одного `app.db` была бы
  неполной (ТЗ п.74, 98). Если файл занят вторым экземпляром программы и переход
  не удался, программа **показывает оператору диалог** и пишет причину в
  `app.log` — молча такая база работать не остаётся.
* **Сбой при запуске виден оператору:** окно с текстом ошибки вместо
  необработанного трейсбека. Приложение оконное (`--windowed`), поэтому
  сообщения в stderr оператор недоступны — всё важное пишется в `app.log`
  рядом с базой.
* **Три раздельных хранилища** (ТЗ п.72): рабочее, комплекты, BACKUP.
* **Выпуск документа и заморозка версии** (ТЗ п.53, 54, 85): перед выпуском
  проверяются обязательные поля и логика дат; выпущенная версия не изменяется
  и не перевыпускается, новая редакция создаётся новой версией.
* **Печать документа по ТЗ** (ТЗ п.55–62): поля и шрифты берутся из описания
  формы, целевой объём страниц объявляется формой, а не кодом вёрстки.
* **Материалы и акты испытаний** (ТЗ п.44, 49): материал проекта относится к
  акту испытаний, и уже связанные акты повторно не предлагаются.
* **Комплекты и реестр** (ТЗ п.69–83): подпапки комплекта, два варианта
  выгрузки, реестр приложений в PDF, нумерация страниц документов.
* **Предэкспортные проверки** (ТЗ п.82, 83): документы, связи, файлы, версии,
  приложения, номера, даты и состав; при ошибках выгрузка либо отменяется,
  либо помечается `Ошибки выгрузки.txt`.
* **BACKUP, проверка и восстановление** (ТЗ п.74, 98): копия отдельной папкой,
  SHA-256 и проверка целостности, перенос на другой компьютер с перезаписью
  путей архива, безопасная замена рабочей базы; интерфейс в настройках.
* **Ведомость состава проекта печатается** (ТЗ п.16): кнопка «Печать состава
  проекта» собирает PDF по разделам рабочего дерева — акты испытаний, АОСР,
  АООК, АОУСИТО, связанные документы, комплекты; те же поля, шрифты и
  нумерация страниц, что у печатных форм (ТЗ п.59, 60, 81).
* **История проекта хранит результаты работы** (ТЗ п.86): версии документов,
  изменения архива, комплекты, реестры и исторические PDF. По событию комплекта
  виден его состав — документы по типам и файлы по категориям, — даже если папка
  выгрузки была перемещена или удалена.
* **Обновление программы без потери данных** (ТЗ п.97): перед миграциями
  создаётся копия, оператор видит отчёт о применённых миграциях; обновление
  со старой схемы сохраняет проекты, документы, версии, архив и историю.
* **ИИ-агент** (ТЗ п.101–106): оператор пишет запрос словами («Проверь комплект
  АОСР №15»), система собирает контекст по белому списку, агент возвращает
  предложения-черновики; данные меняются только после подтверждения и только
  через прикладной API. Нормативные ответы сопровождаются основанием
  (документ, раздел, пункт); без основания заявление остаётся наблюдением.
  Текст файлов архива по умолчанию не передаётся: оператор отмечает нужные
  файлы галочками и подтверждает передачу, система читает их сама и отдаёт ИИ
  текст без путей и хешей (ТЗ п.103). Скан без текстового слоя, неподдерживаемый
  формат и обрезанный текст ИИ называет прямо, а не притворяется, что файл
  проверен. В интернет-режиме передача текста файлов запрещена.
* **Интернет-ИИ GigaChat** (ТЗ п.101): в настройках задаются адрес сервиса,
  модель, область доступа и ключ авторизации; ключ обменивается на
  краткоживущий токен и повторно обменивается по истечении. Ответ модели
  разбирается на те же предложения-черновики, что и в локальном режиме, и
  никогда не меняет данные сам (ТЗ п.104). Без ключа и модели режим честно
  сообщает `not_configured`, а отказ сервиса не подменяется выдуманным
  ответом. Ключ хранится в защищённом хранилище Windows (DPAPI); если система
  не может зашифровать, значение сохраняется открытым, приложение об этом
  предупреждает и переносит ключ в защищённое хранилище при первой возможности.
  Для разработки ключ можно задать переменной окружения
  `EXECUTIVE_DOC_GIGACHAT_KEY`.

## Архитектура и порядок требований

* **Слои (ТЗ п.94, 111, 112).** Интерфейс → прикладные сервисы
  (`app/core/services/`) → хранилище (SQLite + внутренний архив). ИИ — внешний
  компонент, который видит только сервисы, поэтому будущие клиенты (Android,
  Web) получают тот же API, не забирая бизнес-логику документов на себя.
* **Три раздельных хранилища (ТЗ п.108).** Рабочее (`storage/app.db`,
  `storage/internal_archive/`), комплекты оператора (`storage/packages/`) и
  BACKUP (`storage/backups/`). Пути задаёт только `app/config.py`.
* **Приоритет при конфликте требований (ТЗ п.114).** Нормативная форма и
  нормативные требования → сохранность исполнительной документации → история →
  целостность связей → целостность архива → безопасность → ранее утверждённая
  логика → расширяемость → удобство интерфейса → удобство реализации. Поэтому
  вёрстка не ужимается ради числа страниц (ТЗ п.56), а структура нормативной
  формы не перестраивается ради удобства (ТЗ п.62): расширение делается новой
  версией формы (ТЗ п.96).

## Установка и запуск

Требуется Python 3.10+.

```bash
python -m venv venv

# Windows
venv\Scripts\activate
# Linux / macOS
source venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt

python main.py
```

### Запуск на Linux

Приложение полноценно работает на Linux, но запускать его нужно в графической
сессии: Qt требует работающего дисплейного сервера.

```bash
python3 -m venv venv
source venv/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
python main.py
```

Если окно не открывается и в выводе есть сообщение про `xcb`, не хватает
системных библиотек Qt6:

```bash
sudo apt install libxkbcommon-x11-0 libxcb-cursor0 libxcb-xinerama0 \
    libxcb-icccm4 libxcb-image0 libxcb-keysyms1 libxcb-randr0 \
    libxcb-render-util0 libxcb-shape0 fonts-dejavu
```

Данные по умолчанию лежат в `storage/` рядом с `main.py`. Чтобы держать их в
другом месте (например, на отдельном разделе), задайте переменную окружения
`EXECUTIVE_DOC_DATA_DIR`.

**Автономная сборка под Linux** (отдельный каталог, чтобы не смешивать её с
рабочим окружением):

```bash
python3 -m venv buildenv
source buildenv/bin/activate
pip install -r requirements.txt -r requirements-build.txt
pyinstaller --clean --noconfirm ExecutiveDocSystem.spec
./dist/ExecutiveDocSystem/ExecutiveDocSystem
```

Что работает на Linux, а что нет:

| Возможность | Linux | Windows |
|---|---|---|
| Ведение проектов, документов, выпуск версий | да | да |
| Печать в PDF, комплект с реестром, реестр документов | да | да |
| Открытие папки архива кнопкой в интерфейсе | нет — открывайте каталог вручную, путь показывает «Где лежат данные» | да |
| Хранение ключа GigaChat | `~/.local/share` нет: ключ в открытом виде в `storage/settings.json` (предупреждение в интерфейсе) либо в переменной `EXECUTIVE_DOC_GIGACHAT_KEY` | DPAPI, ключ шифруется средствами Windows |
| Сохранённый GigaChat-ключ переносится на другую ОС | нет, вводите заново | нет, вводите заново |

Для GigaChat через служебную сеть задайте прокси переменными окружения
(`HTTPS_PROXY=http://прокси:8080`) — приложение учитывает их при обращении к
сервису.

### Сборка автономного приложения

Описание сборки лежит в репозитории (`ExecutiveDocSystem.spec`), поэтому `.exe`
собирается из свежего клона без дополнительных файлов.

**Windows:** двойной щелчок по `build_windows.bat` (или запуск из командной
строки). Скрипт сам создаёт окружение `buildenv`, ставит зафиксированные
версии из `requirements.txt` и `requirements-build.txt` и собирает приложение.

**Вручную (любая ОС):**

```bash
pip install -r requirements.txt -r requirements-build.txt
pyinstaller --clean --noconfirm ExecutiveDocSystem.spec
```

Результат: `dist/ExecutiveDocSystem/ExecutiveDocSystem.exe` (под Windows) либо
`ExecutiveDocSystem` (под Linux).

> Версии зависимостей зафиксированы: смена версии библиотеки — сознательное
> решение с проверкой тестов, а не случайность сборки.
> Готовый `dist/ExecutiveDocSystem/` **обязательно** собирать на той же ОС,
> для которой он предназначен: сборка под Linux даёт ELF, под Windows — `.exe`.
> Каталог данных создаётся рядом с исполняемым файлом (`dist/.../storage/`).
> **Пересборка `dist/` удаляет каталог данных** — перед пересборкой перенесите
> `storage/` в другое место. Каталог можно также переопределить переменной
> окружения `EXECUTIVE_DOC_DATA_DIR`.

## Где лежат данные

Всё в каталоге `storage/` (три раздельных хранилища, ТЗ п.72):

```text
storage/
├── app.db                 рабочая БД (SQLite)
├── internal_archive/      внутренний архив файлов (одна копия на файл)
├── packages/              сформированные комплекты (выгрузки оператора)
├── backups/               резервные копии (BACKUP)
└── settings.json          настройки приложения
```

Пути вычисляются **только** в `app/config.py`. Зависимости от текущего рабочего
каталога нет: запуск из любой директории, ярлыка или собранного бинарника
работает одинаково.

`storage/` целиком закрыт в `.gitignore` — включая `backups/`, которые содержат
базу, все физические файлы, связи, версии и историю проекта, то есть
персональные данные (ТЗ п.74, 98).

```bash
pytest
```

Ручная приёмка собранного приложения на Windows — `docs/ПРИЁМКА_WINDOWS.md`.
Включение интернет-ИИ и ввод ключа GigaChat — `docs/КЛЮЧ_GIGACHAT.md`
(инструкция для пользователя, ключ вводится в приложении и никому не
пересылается).
Автотесты проверяют логику, но не проверяют шрифт и поля на бумаге и работу
просмотрщика PDF.

Проверка выполняется по этапам, начиная с последнего:

```bash
pytest tests/test_stage8_full_scenario.py    # ТЗ п.110: полный сценарий
pytest tests/test_stage7_*.py                # Этап 7: обновление и ИИ-агент
pytest tests/test_stage5_*.py                # Этап 5: печать, выпуск, комплекты
pytest tests/test_backup_restore.py tests/test_backup_ui.py   # Этап 6
pytest tests/test_stage4_*.py                # Этап 4
pytest tests/test_stage3_*.py                # Этап 3
pytest tests/test_stage2_forms.py            # Этап 2
pytest tests/test_stage1_schema.py           # Этап 1
pytest tests/test_full_suite.py tests/test_archive_and_validation.py   # Этап 0
pytest                                  # всё вместе
pyflakes app tests conftest.py run_demo.py
python run_demo.py                      # сквозная проверка в отдельном каталоге
```

Последняя проверка (2026-09-30): 660 тестов пройдено; `pyflakes` чист,
`run_demo.py` выполняется и завершается сообщением
«ПРОВЕРКА ЗАВЕРШЕНА УСПЕШНО».

Тесты изолированы от рабочего хранилища: `conftest.py` подменяет каталог данных
на временный до импорта приложения, поэтому прогон не может повредить реальным
проектам. GUI-тесты работают в headless-режиме и не открывают модальных
диалогов (иначе тест зависает вместо падения).
