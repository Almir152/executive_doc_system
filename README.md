# Единая система управления исполнительной документацией

Настольное приложение для учёта исполнительной документации строительного
объекта по техническому заданию (115 разделов).

> **Статус разработки.** Закрыты **Этап 0** (запускаемость и целостность),
> **слой данных Этапа 1** (справочники, доменные модели, версии, миграции схемы)
> и **Этапы 2–3** (валидация нормативных форм, рабочее окно проекта с карточкой,
> проектной документацией и историей), а также начало **Этапа 4**: редактор формы
> документа в рабочей области с сохранением черновика.
> Комплекты документов, печать по ТЗ, BACKUP по расписанию и реальный ИИ-анализ
> **ещё не реализованы**. Точный перечень — в разделах «Что уже работает» и
> «Что не реализовано». Не обещайте заказчику то, чего в коде нет.

## Что уже работает (Этапы 0–3)

* **Рабочее окно проекта** (ТЗ п.16): открывается двойным щелчком по проекту;
  показывает карточку, проектную документацию, документы, связанные файлы,
  комплекты и историю. Карточка правится отдельной операцией (ТЗ п.17).
* **Проектная документация** (ТЗ п.21): разделы с неограниченным количеством,
  уникальным кодом внутри проекта и защитой от удаления, если в проекте есть
  выпущенные версии документов.
* **История проекта** (ТЗ п.86): каждое изменение карточки и другие операции
  пишутся в ту же транзакцию, что и сами данные.
* **Редактор формы документа** (ТЗ п.65): открывается в рабочей области окна
  проекта, поля строятся по описанию нормативной формы (ТЗ п.96), а не по коду.
* **Черновик незавершённой формы** (ТЗ п.66): сохраняется без проверки
  обязательных полей; при закрытии формы с несохранённым вводом предлагается
  сохранить черновик, отменить закрытие или закрыть без сохранения.
* **Выбор справочных значений с поиском** (ТЗ п.20): организации, представители
  и виды разделов выбираются из справочника с поиском по мере набора, в любом
  регистре кириллицы. Свободный ввод для справочных значений недоступен.
* **Создание и правка раздела** (ТЗ п.21, 22): один диалог с реквизитами
  раздела, выбор вида раздела, организации и проектировщика — с поиском;
  код раздела при правке не меняется, так как он участвует в именах папок
  комплекта (ТЗ п.70).
* **Выбор разделов проекта в форме** (ТЗ п.21): поле со ссылкой на разделы
  заполняется отметкой нужных разделов, а не текстом; выбор сохраняется
  вместе с черновиком.
* **Блоки подписантов** (ТЗ п.63): «Сдал» и «Принял» — два независимых блока,
  каждый заполняется или не заполняется сам по себе.
* **Незаполненный представитель эксплуатации** (ТЗ п.64): решение «оставить
  пустую строку» или «убрать блок из печати» предлагается перед сохранением,
  относится к конкретному документу и сохраняется в одной транзакции с
  черновиком. Убрать блок можно только там, где это допускает форма
  (АОУСИТО и акты испытаний, ТЗ п.40); в остальных формах вопрос не задаётся.

* **Проекты:** создание, просмотр, удаление с подтверждением. Направление работ
  из ТЗ п.14 (общестроительные / внутренние сети / наружные сети).
* **Единый архив файлов** с дедупликацией по SHA-256: один физический файл —
  одна копия на диске (ТЗ п.84, 92). Повторная загрузка того же файла новой
  копии не создаёт.
* **Архив разделён на два уровня** по ТЗ п.90, 91: логический `ArchiveDocument`
  и физические версии `ArchiveFileVersion`. Одна копия файла на версию.
* **Версии файлов:** новая редакция схемы создаёт новую версию, а прежняя
  сохраняется (ТЗ п.53, 93). Актуальной помечена ровно одна версия.
* **Связи с ролями и закреплением версии** (ТЗ п.47, 49, 91): одна схема
  связывается с любым числом актов, и уже сформированные комплекты продолжают
  ссылаться на ту редакцию файла, которая использовалась при их создании.
* **Доменные модели по ТЗ п.89:** организации и представители, разделы проекта,
  материалы, документы с подтипами АОСР/АООК/АОУСИТО/акт испытаний, блоки
  подписантов «Сдал»/«Принял», комплекты с нумерацией реестра, история.
* **Нормативные формы описаны как данные** (ТЗ п.24, 96) и загружены в
  справочник `normative_forms`: АОСР, АООК, АОУСИТО и акт испытаний. Форма
  задаёт разделы, источник каждого значения (вручную / из проекта / из архива),
  неизменяемые формулировки и правила вроде порога «5 документов -> реестр».
  Перед сохранением описание проверяется на соответствие ТЗ: форма, нарушающая
  п.25-28, 30-32 или 35-41, в базу не попадает.
* **Версионирование форм** (ТЗ п.96): изменение формы под занятым номером
  версии отклоняется — требуется новая версия; прежняя остаётся в базе, и
  документы, выпущенные по ней, сохраняют её.
* **Версионирование схемы БД** (ТЗ п.97): миграции применяются один раз,
  фиксируются в `PRAGMA user_version`, каждая — в своей транзакции.
* **Защита от потери файлов:** архивные документы не удаляются каскадом вместе
  с проектом — ограничение держит сама БД (ТЗ п.54, 109).
* **Категории архива** по ТЗ п.50: материалы и документы качества,
  исполнительные схемы, протоколы и обследования, архив проекта.
* **Защита от удаления используемого файла** (ТЗ п.50, 109).
* **Проверка хронологии АООК ↔ АОСР** (ТЗ п.33, 87) — как библиотечная функция;
  подключение к формам запланировано в Этапе 4.
* **AI Connector:** три режима по ТЗ п.9 (нет ИИ / локальный / интернет-ИИ) с
  индикацией; при «Нет ИИ» чат скрывается. ИИ не имеет доступа к БД и файлам.
* **Целостность БД:** внешние ключи проверяются при каждом подключении, и если
  прагма не сработала (файл базы занят другим процессом), программа отказывается
  работать с понятным сообщением, а не продолжает без контроля связей.
* **Обычный режим журнала SQLite:** база принудительно выводится из WAL, иначе
  последние коммиты лежали бы в `app.db-wal` и копия одного `app.db` была бы
  неполной (ТЗ п.74, 98). Если файл занят вторым экземпляром программы и переход
  не удался, программа **показывает оператору диалог** и пишет причину в
  `app.log` — молча такая база работать не остаётся.
* **Сбой при запуске виден оператору:** окно с текстом ошибки вместо
  необработанного трейсбека. Приложение оконное (`--windowed`), поэтому
  сообщения в stderr оператор недоступны — всё важное пишется в `app.log`
  рядом с базой.
* **Три раздельных хранилища** (ТЗ п.72): рабочее, комплекты, BACKUP.
* **Выгрузка реестра** в PDF (базовая версия, будет переработана в Этапе 5).

## Установка и запуск

Требуется Python 3.10+.

```bash
python -m venv venv

# Windows
venv\Scripts\activate
# Linux / macOS
source venv/bin/activate

pip install --upgrade pip
pip install -r requirements.txt

python main.py
```

### Сборка автономного бинарника

```bash
# Windows
pyinstaller --noconfirm --onedir --windowed --name ExecutiveDocSystem main.py
# Linux
pyinstaller --noconfirm --onedir --windowed --name ExecutiveDocSystem main.py
```

> Готовый `dist/ExecutiveDocSystem/` **обязательно** собирать на той же ОС,
> для которой он предназначен: сборка под Linux даёт ELF, под Windows — `.exe`.
> Каталог данных создаётся рядом с исполняемым файлом (`dist/.../storage/`).
> **Пересборка `dist/` удаляет каталог данных** — перед пересборкой перенесите
> `storage/` в другое место. Каталог можно также переопределить переменной
> окружения `EXECUTIVE_DOC_DATA_DIR`.

## Где лежат данные

Всё в каталоге `storage/` (три раздельных хранилища, ТЗ п.72):

```text
storage/
├── app.db                 рабочая БД (SQLite)
├── internal_archive/      внутренний архив файлов (одна копия на файл)
├── packages/              сформированные комплекты (выгрузки оператора)
├── backups/               резервные копии (BACKUP)
└── settings.json          настройки приложения
```

Пути вычисляются **только** в `app/config.py`. Зависимости от текущего рабочего
каталога нет: запуск из любой директории, ярлыка или собранного бинарника
работает одинаково.

`storage/` целиком закрыт в `.gitignore` — включая `backups/`, которые содержат
базу, все физические файлы, связи, версии и историю проекта, то есть
персональные данные (ТЗ п.74, 98).

## Тесты

```bash
pytest
```

Тесты изолированы от рабочего хранилища: `conftest.py` подменяет каталог данных
на временный до импорта приложения, поэтому прогон не может повредить реальным
проектам. GUI-тесты работают в headless-режиме и не открывают модальных
диалогов (иначе тест зависает вместо падения).
